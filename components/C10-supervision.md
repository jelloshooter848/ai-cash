# C10 — supervision

**Module:** `aicash/supervision.py` (+ routes in mintapi) · **Tests:** `tests/test_c10_supervision.py` · **Spec:** §5.2, §5.3, §6.1, §7.3 (custodial rules), §8(c) · **Locked:** L13, L17 · **Depends:** C04, C05, C06

## Purpose
The optional Supervision Profile: custodial accounts under operator identities, the seven operations, and signed statements. Mounted onto a C06 server (profile advertised in descriptor).

## Public API (Python)
```python
class SupervisionServer(MintServer):          # a C06 mint with the profile mounted
    def __init__(self, config: MintConfig, ledger: Ledger,
                 registration_token=REGISTRATION_INHERITS_ISSUANCE): ...
        # Same constructor contract as MintServer (including the boot-time
        # config/ledger consistency check on burn_policy / recovery_window_ms /
        # max_lock_expiry_ms). The descriptor's `profiles` gains "supervision"
        # automatically when mounted — the config passed in need not list it
        # (requirement 8); an explicitly listed "supervision" is not duplicated.
        # `registration_token` gates POST /v3/operator/register: a non-empty
        # secret string, REGISTRATION_OPEN, REGISTRATION_DISABLED, or (the
        # default) REGISTRATION_INHERITS_ISSUANCE. Anything else raises here,
        # not at the first request.
    def start(self, port=0, host="127.0.0.1") -> int   # returns the bound port;
                                # Layer 0 (C06) and supervision on the same port
    def stop(self) -> None
    def provision_operator(self, name) -> (operator_id, operator_key)
                                # OUT-OF-BAND bootstrap: creates an operator in
                                # process, no credential, no HTTP. Works with
                                # registration disabled — that is what it is for.
    registration_token: str | None      # what the route requires, or None when
                                        # it is open or disabled
    registration_source: str            # "inherited" | "inherited-open" |
                                        # "generated" | "explicit-token" |
                                        # "explicit-mode"

def make_supervision_mint(config, db_path, clock=system_clock,
                          registration_token=REGISTRATION_INHERITS_ISSUANCE)
                                # -> (SupervisionServer, Ledger); C06's make_mint
                                # for a supervised mint. Both halves built from
                                # the one config, so the descriptor and the
                                # ledger cannot disagree.
```
These four names live on `aicash.supervision`, not on the package root: `aicash/__init__.py` mirrors this module's `__all__`, which stays `["SupervisionServer"]`.
**Time:** supervision has no clock parameter anywhere — all supervision time (cap windows, pull expiry, statement periods, journal timestamps) flows from the Ledger's injected clock, observed through `Ledger.status` (L17). Inject a `FakeClock` into the Ledger and the whole supervised mint moves with it.

## Public API (HTTP, under the C06 server)
```
POST /v3/operator/register            registration-auth (X-Registration-Token, or X-Admin-Token); {operator_name} -> {operator_id, operator_key}
POST /v3/operator/agents              op-auth; {agent_name} -> {agent_id, agent_key}
POST /v3/operator/caps                op-auth; {agent_id, per_hour_mc|null, per_day_mc|null, absolute_mc|null}
POST /v3/operator/freeze | unfreeze   op-auth; {agent_id | "ALL"} -> {status:"ok", frozen:[...]} / {status:"ok", unfrozen:[...]}
POST /v3/operator/flags               op-auth; {agent_id, no_bearer_withdrawal: bool}
GET  /v3/agent/balance                agent- or op-auth; ?agent_id -> {balance_mc, spend_rate...}
POST /v3/agent/authorize_pull         agent-auth; {payee_account, cap_mc_per_day, expires_at} -> {auth_id}
POST /v3/agent/revoke_pull            agent-auth; {auth_id}
POST /v3/pull                         payee-agent-auth; {auth_id, amount_mc, ref}
POST /v3/agent/transfer               agent-auth; {to_account, amount_mc, ref}     (custodial→custodial)
POST /v3/agent/deposit                agent-auth; {tokens:[...]}                    (bearer→balance, via C04)
POST /v3/agent/withdraw               agent-auth; {outputs:[{amount_mc, secret_hash}]}  (balance→bearer, via C04)
GET  /v3/operator/statement           op-auth; ?agent_id|fleet&from&to -> §6.1(7) signed statement
```
**Registration is credential-gated, on its own credential (pre-1.0 fix, revised).** `/v3/operator/register` was authless and labelled a test bootstrap. It is not a test bootstrap: registering an operator creates a supervision perimeter that no existing operator's caps, freeze or flags reach, so an authless one is an authless way *out* of every per-agent control the profile has — the holder of a no-bearer-withdrawal agent registered an operator of its own, registered an agent under it, transferred the allowance across and withdrew it as bearer.

The first fix gated the route on C06's issuance check (`X-Admin-Token`, the `/admin/issue` credential). That closed the hole and opened a second one, because **creating an operator account and creating credits from nothing are two different powers**. On a mint built `ADMIN_ISSUANCE_DISABLED` the issuance check is unconditionally false, so registration answered 401 to no credential, an empty one, a wrong one and the literal name of the mode alike. With no operator there are no agents, no deposits, no pulls, no withdrawals and no statements: the profile mounted, advertised itself in the descriptor and could do nothing at all — in exactly the configuration the rest of this work pushes operators toward. This document and the module both said such a mint "provisions operators out of band"; **no out-of-band mechanism existed anywhere in the repository** — the only writer of `sup_operators` was the gated route, and the launcher had no supervision flag.

The route therefore has its own credential, `SupervisionServer(..., registration_token=...)`, with C06's three-named-state discipline and its own header `X-Registration-Token`. The default still gives a deployment ONE answer to "who administers this mint" wherever one exists:

| `admin_token` | default registration gate | `registration_source` |
|---|---|---|
| a secret string | the SAME secret; `X-Admin-Token` still accepted, unchanged | `inherited` |
| `ADMIN_ISSUANCE_OPEN` | open too (a gated route next to an unauthenticated minting endpoint is theatre) | `inherited-open` |
| `ADMIN_ISSUANCE_DISABLED` | a **generated** credential, at `server.registration_token`, never logged | `generated` |

An explicit `registration_token=` overrides all of it: a secret string (the two powers held by two different people), `REGISTRATION_OPEN` (unauthenticated, opted into by name, announced as a WARNING), or `REGISTRATION_DISABLED` (401 to everyone — and honest now, because `provision_operator` is the out-of-band mechanism). The credential is compared with `hmac.compare_digest`, never `==`. A supervision bearer key — operator or agent — is not that credential and gets 401, not 403. Which state applies is logged once at mount by `aicash.supervision`, and the credential itself never appears in a log record.

**In the launcher.** `run_mint.py --supervision` mounts the profile; `--registration-token`, `--open-registration`, `--no-registration` and `--provision-operator NAME` map onto the states above, and `--no-issuance` (new) builds the `ADMIN_ISSUANCE_DISABLED` mint that the finding is about — a configuration this launcher could not produce at all before. A generated registration credential and any provisioned operator key are written to a 0600 `--supervision-keys-file` after the bind, the same discipline as the issuance credential, and printed only under `--show-supervision-secrets`.

**Wire fix (pre-1.0):** the freeze/unfreeze response field listing the affected agent ids was originally misspelled `freezed`/`unfreezed`; it is now `frozen`/`unfrozen`. Renamed before 1.0 while no external caller could depend on it — no compatibility alias is served. The §6.1(7) journal *kinds* were always `freeze`/`unfreeze` and are unchanged.

## Error envelope
Supervision-level rejections are FLAT — `{"status": "rejected", "reason": "<code>"}` — not the §3.8 `errors` array (there are no batch indices to enumerate). Three shapes exist:
* `401 {"status": "unauthorized"}` — no key / unknown key on an authed route, and any request to `/v3/operator/register` without the mint's `X-Admin-Token` (a valid supervision key is the wrong KIND of secret there, not the wrong role — answering 403 would confirm the key was recognised); `403 {"status": "forbidden"}` — a valid key of the wrong role (also: an agent querying another agent's balance).
* `400/404 {"status": "rejected", "reason": ...}` — the supervision-level rejections below. **An integer the mint cannot store is one of them, not a 500.** Python's `int` is unbounded and SQLite's `INTEGER` is signed 64-bit, so `{"per_hour_mc": 9223372036854775808}` is valid JSON of the correct type that used to pass every guard on the route, reach `conn.execute`, raise `OverflowError` out of the driver and land in the blanket handler as a bare 500. §3.8 owes an enumerated reason, so the range lives on `_plain_int` — the single predicate every integer field already goes through — rather than on the five fields the report happened to name. `unknown_agent` is served as 404 (and deliberately identical for "no such agent" and "another operator's agent" — no cross-operator existence oracle); everything else is 400.
* Pass-through: when a deposit/withdraw's underlying C04 exchange rejects, the response is the §3.8 form `400 {"status":"rejected", "errors":[{index,kind,reason},...]}` verbatim.

**Body framing is NOT part of the envelope split.** C10 has its own reader (`_read_sup_json`) so it can answer a refused body in the flat vocabulary above instead of C06's `errors` array, and its own copy of the byte cap. The shared *verdict* about which bodies are unframable is C06's single `_body_framing_is_unreadable`, which both readers call: the two servers share one socket, so a shape Layer 0 reads and the profile refuses (or the reverse) is a request-smuggling gap in whichever half is laxer.

**And that verdict is not enough on its own, because it asks the parsed headers for a header BY NAME.** `self.headers` is not the wire — it is what `email.parser` made of the wire, and the two differ on inputs an intermediary reads perfectly well. email's header-line regex is `[\041-\071\073-\176]*:`, which excludes SP and HTAB, so **one space before the colon** makes `Transfer-Encoding : chunked` stop being a header, and takes every line after it into the message *payload*. `get("Transfer-Encoding")` answered None, the length defaulted to 0, the body read as empty, the route answered — and the chunk octets stayed on a keep-alive socket to be framed as the next request line. (The smuggled request's answer carries no status line at all: `parse_request` fails before learning a version, so `send_error` writes a bare HTML page — one request in, two answers out, and a status-line count sees one.)

So C10 adds `_sup_framing_is_unreadable`, stated about the **view** rather than about any header name. It asks one question — *can this layer prove the header block in front of it means, to every other hop, exactly what it means here?* — and only a yes may reuse the connection. Four ways the proof fails: the parser recorded a **defect**; the header block left a non-empty **payload**; a name or value carries **CR/LF** (obs-fold — RFC 7230 §3.2.4 says reject rather than guess which reading the next hop took); or a **name this layer cannot prove is read the same way everywhere**.

**That fourth clause is a normalisation, not a list — and the first attempt at it was a list.** It normalised with `strip().lower()` and compared against two literal spellings, which outside review broke by walking one step off the reported shape rather than by inventing a new one. `Transfer_Encoding: chunked` beside `Content-Length: 0` parses *perfectly*: no defect, no payload, no fold, one clean header registered under the name `Transfer_Encoding` — so the first three clauses were silent, `transfer_encoding != transfer-encoding`, and the stated length of `0` was believed. Every front end, CGI gateway and WSGI server that round-trips a header through an environment variable folds `_` to `-`, so that request is chunked to them and empty to us. The neighbouring field mentions no transfer coding at all: `Content_Length: 125` on a GET declares a body to them and nothing to us, and a GET has no "no computable length" backstop to fall through to. `Transfer-Encoding;:` and `Transfer-Encoding.:` do the same by punctuation.

So the clause now:
* requires every parsed header name to be a bare RFC 7230 `token` (**tchar** only) — a name carrying `;`, `"`, a space or a control byte is one no two parsers must agree on, whatever it means;
* **folds** each name hard (lowercase, every non-alphanumeric character dropped, so `-`, `_`, `.` and repeats of them all vanish) and, when the fold lands on `contentlength` or `transferencoding` under a name that is *not* the canonical spelling, **refuses on the fold** rather than trusting either reading;
* refuses a canonical `transfer-encoding` outright, because nothing in this stack dechunks.

Everything a hop reads as `Content-Length` or `Transfer-Encoding` — by any spelling that survives tokenisation, or any separator that survives folding — is refused. The residual is bounded and named: a header that is a clean token, folds onto nothing HTTP calls framing *today*, and is nevertheless treated as framing by some future hop. Nothing at this layer can see that one.

**One chokepoint, all four paths.** The rule is not bolted onto the two C10 readers; it narrows `_framed_body_length`, the single method every framing decision in this server is built on (`_body_framing_is_unreadable` *is* `… is None`; the POST reader asks that; `_close_if_body_goes_unread` asks both). The C10 override refuses on the C10 rule and otherwise **delegates to `super()`** — strictly additive, never the other way — so the C10 POST routes, the C10 GET routes **and the inherited Layer 0 routes served on the same socket** are all covered by one rule with no second copy of the length arithmetic. That matters because the earlier version left the GET half with a name check and no length rule behind it at all, and left `/v3/exchange`, `/admin/issue` and `/v3/mints` on a supervision mint framing shapes the profile refused — a stricter profile beside an open door is not a defence. `_body_framing_is_unreadable` itself is deliberately *not* overridden: it stays the one shared verdict both readers ask, and returns C10's stricter answer because the count under it does. C06 is closing the same class in its own file this round, with a differently shaped rule (a confusable-**name** regex: each hyphen of a framing header name becomes "any one character, or none"). The override is not waiting on it and does not duplicate it — C10's fold is the wider of the two by construction, because it drops *every* non-alphanumeric character rather than one per hyphen position and refuses any name that is not an RFC 7230 token at all, so `Content--Length`, `Content-Length;`, `Transfer-Encoding;` and `Transfer-Encoding.` are refused on a supervision mint whether or not a regex of that shape reaches them. Keeping both means the profile's answer does not depend on which spellings the other half currently covers, which is precisely the property that was missing when this class was found. Envelope differs, framing does not.

## Recipe: fund a custodial fleet
From an empty mint to spendable agent balances (what an operator's bootstrap script does):
0. Get the registration credential. On a mint with a string `admin_token` it IS that secret (nothing to do). On a mint with issuance disabled it was generated at mount: read `server.registration_token`, or the `registration_token` field of `run_mint.py`'s `--supervision-keys-file`. With registration disabled there is no step 1 — call `server.provision_operator(name)` (or start with `--provision-operator NAME`) and skip to step 2 with the key it returns.
1. `POST /v3/operator/register {"operator_name": ...}` with that credential in **`X-Registration-Token`** (or `X-Admin-Token` where the two are the same secret) → keep `operator_key`; `POST /v3/operator/agents` per agent → keep each `agent_key`.
2. Mint bearer value via C06's non-normative `/admin/issue` (with `X-Admin-Token` if configured). On a mint with issuance disabled, fund through `Ledger.issue(...)` in process instead — §7.1 operator funding is an in-process act there for the same reason `provision_operator` is. Simplest: generate `secret = new_secret()` yourself and issue **by-hash** `{"amount_mc": N, "secret_hash": ledger_key(secret)}` (the by-secret wire form also works — the mint hashes and discards).
3. Build the token string with C01: `token = format_token(mint_id, N, secret)`.
4. `POST /v3/agent/deposit {"tokens": [token]}` with the agent's key → the mint runs a real §5.3 exchange into custody and credits the balance net of the deposit burn (`deposited_mc`, `burn_mc` in the response).
Thereafter transfers/pulls are burn-free custodial moves; withdrawals return bearer tokens by-hash.

## Requirements
1. **Auth separation (§6.1(1)):** operator and agent keys are distinct random bearer keys; agent keys cannot call operator routes (403), and vice versa for agent-private routes. Supervision controls bind only registered agents (L13) — Layer 0 routes stay authless.
2. **Caps (§6.1(2)):** rolling trailing windows 3600s/86400s, evaluated at commit with the injected clock; ALL debit kinds count: transfer, pull_out, withdrawal gross (amount + burn). Absolute = lifetime total. Exceeding → `agent_cap_exceeded`, atomic (no partial debit).
3. **Freeze (§6.1(3)):** per-agent and operator-wide; frozen accounts fail every outflow (transfer, withdraw, pull against them) with `account_frozen`; nothing queues; credits IN to a frozen account still land.
4. **No-bearer-withdrawal flag (§6.1(4)):** while set, `/v3/agent/withdraw` fails with `withdrawal_disabled`. Deposits still allowed. The flag also refuses the flagged agent's custodial moves that leave its operator — `/v3/agent/transfer` to another operator's agent, and `/v3/agent/authorize_pull` of a grant whose payee is another operator's agent — with `external_transfer_disabled`, a reason this component adds; neither route has a pinned error enumeration in §6.1. `/v3/pull` on such a grant is refused too, re-checked at pull time since a grant may predate the flag — with a different reason; see the error-vocabulary note below. §6.1(4) names only withdrawals, and refusing only withdrawals does not do the job the flag is claimed to do: a transfer to an agent under an operator this operator does not supervise is the same exfiltration with one hop inserted. Moves to a SIBLING agent of the same operator stay legal, because the receiver is inside the same perimeter (same caps, freeze, flags, fleet statement) and the operator can flag it too. **The bound this buys is "value cannot leave the operator", not "the allowance cannot become bearer":** an unflagged sibling can still withdraw, so what bounds total exfiltration inside a fleet is the cap schedule (requirement 2) and the freeze (requirement 3), not this flag.

   **Error vocabulary, and why /v3/pull differs.** `external_transfer_disabled` is a reason this component adds; `/v3/agent/transfer` and `/v3/agent/authorize_pull` may carry it because §6.1 pins no error enumeration for either. `/v3/pull` may not: **§6.1(6) pins a CLOSED list** — `authorization_missing | authorization_revoked | authorization_expired | pull_cap_exceeded | agent_cap_exceeded | account_frozen | insufficient_balance` — and the spec is ratified, so a conformant client switch-casing those seven must never meet an eighth. The flagged pull therefore answers `authorization_revoked`, the member of that list that is true here: the grant confers no debit right any more, and the client behaviour it asks for (stop pulling; ask the granter for a new authorization) is exactly right, since a fresh grant is what the granter would need and would itself be refused `external_transfer_disabled` at authorize time. The stored authorization row is deliberately NOT marked revoked — clearing the flag must restore the grant, and a real revoke is the granting agent's act under §6.1(6)'s "revocable-at-will" — and no route reports that bit, so nothing observable disagrees. `account_frozen` was rejected as the mapping precisely because something observable *would* disagree: `/v3/agent/balance` publishes `frozen`, and this account is not frozen. Side benefit: the payee is told nothing about the granter's operator or flags, which naming the flag leaked to a third party.
5. **Pulls (§6.1(6)):** payee must be a custodial account at this mint; atomic debit+credit; enforce `pull_cap_exceeded` (per-auth trailing day), `authorization_missing|revoked|expired`, granting-agent caps, freeze; revocation is immediate.
6. **Custodial/ledger bridge (§5.3):** deposit spends bearer tokens into mint custody via a real C04 exchange (tokens → mint-internal by-hash outputs) crediting the balance; withdraw debits balance then creates caller-specified by-hash outputs via C04 issue-like exchange from mint custody. Custodial internal transfers/pulls never touch C04 and never burn (§7.3); deposits/withdrawals burn as the exchanges they are — the withdrawing agent is charged `compute_burn(amount_withdrawn)` on the requested amount, never on the mint-selected custody inputs; any ledger-level burn difference is absorbed by the mint (§7.3, R17).
7. **Statements (§6.1(7), §8(c)):** exact pinned schema; kind partition as specced (withdrawal net-of-burn + separate burn line, freeze/unfreeze amount 0 excluded from sums); signed with the mint key (C05); balance invariant enforced at generation; producible on demand for any in-retention period.
8. Descriptor gains `"supervision"` in `profiles` when mounted.
9. All state in the mint's sqlite; atomicity via transactions on the shared connection discipline used by C04.
10. **Caller-supplied strings (`_plain_text`):** every string a caller can put into a supervision column, get echoed back, or have re-rendered inside a signed statement goes through ONE predicate, stated about the value rather than about the field, so a field added later inherits it by being passed through it. Three requirements, because that is what such a string is for:

    | requirement | clause | why |
    |---|---|---|
    | **bounded** | `len(v) <= MAX_TEXT_LEN` (256) | there is no storage reason for a bound, which is exactly why there was none. A 5,000-character `operator_name` returned 200 and made a real operator; a `ref` of that size is written to TWO journal lines per transfer and re-rendered in every signed statement covering them, forever. A field with no bound has its cost set by its caller. 256 is generous for what these fields *are* — human labels and payment references, not documents — and is one number rather than one per field. |
    | **encodable** | `v.encode("utf-8")` | the operation the sqlite binding and the response encoder both perform. An unpaired surrogate (`"op\ud800"` — `json.loads` produces it happily, JSON's `\uXXXX` escape having no pairing rule) used to reach the database and fail on the way *out*, with the operator, the row and the bearer key already created and `§3.8` owing an enumerated reason it could no longer give. Asked here by DOING it, never by pattern-matching what a surrogate looks like. |
    | **renders, and forges no structure in anything that embeds it** | `v.isprintable()` | encodability is a question about bytes; these fields need a question about a string. `"acme\u0000evil"` encodes fine and is under the bound, and it answered 200 with a real operator and a live key — as did BEL, BS, TAB, CR, LF, ESC, DEL, the C1 controls, U+2028/9, NBSP, the bidi overrides, the zero-width format characters and the private-use area. `str.isprintable()` is false for exactly that set: the code points with no rendering of their own, and the ones whose rendering is an instruction to the display rather than a glyph. |

    **The field this matters most for is `ref`, and it is the only one that reaches a signature.** Names do not: a statement's `scope` carries `operator_id` and `agent_id`, both mint-generated, and no route echoes `sup_operators.name` or `sup_agents.name` at all. `ref` is written by the *agent*, copied onto both journal lines of a transfer or pull (and the one line of a deposit), and re-rendered inside every signed statement covering that period. A signature over a document whose text was chosen by the party the document audits is worth less if that text can carry an ESC sequence into the reader's terminal, a line separator into a line-oriented export, or a bidi override that makes the rendered `ref` read as something other than what was signed. C01's canonical JSON escapes the C0 controls, so JSON structure itself was never forgeable — but it does not escape DEL, the C1 range, U+2028/9 or the format characters, and JSON is one embedding of many. The refusal belongs on the way in, where the answer is still "no".

    **Known residual, measured this round and NOT C10's to close: the access log is one layer down and enforces none of this.** `mintapi._Handler.log_request` formats `self.command` — the caller's raw request-line method — straight into the record the profile inherits, and `run_mint.py` writes that logger to `mint-access.log`, the file DEPLOYMENT.md tells the operator to read. Driven against a live supervision mint: `G\x1b[31mET /v3/mints HTTP/1.1` logged `G\x1b[31mET <unknown> 501` with a live ESC octet, and `GE\x00T /v3/agent/balance HTTP/1.1` logged a record containing a NUL. That is the harm this requirement names — an ESC sequence into the operator's terminal — reached by an unauthenticated peer through a field C10 never sees, so the fix is a `log_request` that renders the method (or logs the route alone, as its own docstring already claims it does) in `aicash/mintapi.py`, not a second copy of the rule on `_SupHandler`. The operator console and the operator GUI make `log_message` a deliberate no-op and are clean; the mint is the layer out of step.

Refusal is `400 bad_format` on the routes that name the field, and `404 unknown_agent` / `unknown_account` where the string is an identifier being looked up — an id this mint cannot render is an id it cannot be holding, so "not found" is the true answer and not merely a quieter one (and it is the same answer another operator's real agent gets, so nothing new leaks). **`SupervisionServer.provision_operator` applies the same predicate**, raised as `ValueError` rather than answered: it writes the same column, and the reason that column has a rule is a property of the column and of everything downstream of it, not of who was trusted to fill it. One column is now written from the ROW rather than from the request: `sup_pull_auths.payee_account` used to store the caller's own bytes after `_agent(payee)` had matched a row with them, which is safe only because SQLite TEXT equality is byte-exact — a fact about the storage engine, not about this code. The INSERT stores the resolved row's mint-generated `agent_id`, so "every string in that column is an id this mint issued" is a property of the INSERT. Strings validated *elsewhere* by a stricter grammar are deliberately not re-validated here: deposit `tokens` by C01's `parse_token`, withdraw `outputs[].secret_hash` by `b64u_decode(expect_len=32)`, integers by `_plain_int`, and the bearer keys by digest comparison alone (never stored raw).

## Benchmark (critic checklist)

The wire spelling is `GET /v3/mints\r\n` and nothing else, and on this profile (as on the plain mint, the operator console and the operator GUI) it gets **zero bytes**: the parent computes its two-word verdict before `super().parse_request()` and acts on it after, and `super().parse_request()` reads the header block, so a real 0.9 client blocks in `parse_headers` until the handler's 10 s budget closes the socket. Measured 2026-09-17, 25 cells in parallel: `GET <route>\r\n` and the bare-LF spelling 10.01–10.02 s / 0 bytes on /v3/mints, /v3/agent/balance, /v3/operator/statement and an unrouted path; `POST <route>\r\n` a framed 400 in 0.01 s (CPython refuses a two-word non-GET line *before* the header read, so GET — the only method 0.9 ever had — is the one that goes unanswered); two and five leading empty lines 0 bytes at 0.01 s, the well-formed request behind them discarded, while ONE leading empty line is answered. The sweep is driven anyway and pins what is true either way: never a naked body, never a signature or the descriptor on a 0.9 line, never the stdlib's HTML page, one framed answer or none, and the thread released at the budget. **The fix belongs in `mintapi._Handler.parse_request`** — act on the two-word verdict before calling `super()`, and make the single-empty-line tolerance a bounded loop inside the existing deadline — because all four servers reach or copy that class; a `parse_request` on `_SupHandler` would close the door on the one server that already inherits every other transport refusal and leave the other three open, which is the drift this component has paid for three times, and `test_the_profile_holds_no_request_line_rule_of_its_own` asserts it by identity. Verified by patching that ordering in at runtime: the 0.9 cells become framed 400s in 0.01–0.02 s, the leading-empty-line cells are answered in 0.01 s, and the C10 block passes unchanged. `GET <route>\r` (CR only) stays 0 bytes at the budget under the fix too, and correctly: a lone CR is not a line terminator, so no complete request line was ever asked — the only thing owed there is the bound, and it fires.
