# AICash — A Layered Bearer E-Cash Stack for AI-to-AI Value Exchange

**Status:** draft v0.2
**Supersedes:** v0.1 (single-document protocol)
**Change summary:** restructured from one protocol into a four-layer stack; committed to a default issuance policy; added a reference unit; added exactly one new ledger primitive (hash-lock-or-timeout); added an optional custodial holding mode; moved receipts, escrow, and markets out of the ledger entirely.

---

## 0. Read this first — what AICash is and is not

**AICash credits are closed-loop and nonconvertible.** They cannot be redeemed for dollars, Bitcoin, or any other asset with an independent market price. They buy exactly one class of thing: services offered by other agents and operators participating in this system.

If you need to pay an ordinary commercial vendor who bills in dollars, **AICash cannot do that**, and no configuration of it will. That is a deliberate design constraint, not a missing feature — nonconvertibility is what keeps the protocol out of money-transmission regulation (see §9). A fiat or BTC bridge is possible, but only as a separately operated, separately licensed service at Layer 3, run by an entity that has taken on that regulatory burden. It is not part of this spec and never will be.

This is stated first because reviewers of v0.1 consistently had to infer it from a non-goals table halfway down the document.

## 1. Design goals

- **Simple ledger, capable stack.** The trust-critical component (the ledger) stays small enough to audit in an afternoon. Complexity lives in optional layers above it, where it can be swapped, competed over, or ignored.
- **Built for machines.** Sub-100ms settlement, tokens small enough to sit in a tool-call argument, no human-facing wallet ceremony.
- **Bearer by default, account by choice.** Possession-is-ownership is the primitive. Agents who would rather trade unlinkability for recoverability can opt into a custodial balance instead (§5).
- **Nobody is forced into someone else's tradeoff.** Privacy, accountability, escrow, and recoverability are layer choices made per agent, not global protocol decisions.
- **Federation-ready, not federation-first.** Beta runs as a single trusted mint. The token format keeps the upgrade path open (§10).

## 2. The stack

| Layer | Name | What lives here | Trust required |
|---|---|---|---|
| **0** | Ledger | Bearer tokens, atomic exchange, double-spend prevention, hash-lock/timeout | The mint operator |
| **1** | Holding | Bearer wallets; optional custodial balances | The mint operator (custodial mode only) |
| **2** | Assurance | Signed receipts, escrow agents, reputation, dispute resolution | Whoever you choose, per transaction |
| **3** | Markets | Pricing, auctions, lending, external bridges | Whoever you choose; bridges are separately licensed |

The layering is the central structural change from v0.1. Most apparent conflicts in the design — privacy vs. auditability, simplicity vs. conditional payment, bearer finality vs. crash recovery — dissolve once they are allowed to be resolved at different layers by different parties rather than decided once for everyone in the ledger.

**Layer 0 is the only mandatory layer.** Everything above it is optional and independently replaceable.

## 3. Layer 0 — Ledger

### 3.1 Token format

```
token := aicash:v2:<mint_id>:<amount>:<secret>
```

- `secret`: 32 random bytes, base64url. Generated by the holder, never by the mint.
- `amount`: unsigned integer. Smallest unit = 1 credit. No floats, ever.
- `mint_id`: abstract minting authority — one server in beta, a federation later, with no client-side format change.

A token is a **bearer claim**: whoever holds the secret owns the value. The string can be copied infinitely; only the first party to redeem the underlying secret gets the value. **A token is a password. Treat it as one** — never log it, never put it in a URL query string, never cache it in plaintext.

### 3.2 Ledger state

```
hash(secret) -> {
  amount: int,
  spent: bool,
  lock: null | { preimage_hash: bytes, expiry: timestamp, refund_hash: bytes },
  created_at, spent_at
}
```

The mint stores hashes, never secrets. It therefore cannot spend anyone's money; it can only answer whether a given secret has already been redeemed.

### 3.3 `POST /v2/exchange`

The one endpoint that does everything: pay, split, merge, make change.

```
Request:
{
  idempotency_key: "uuid",
  inputs:  [ "aicash:v2:...", ... ],
  outputs: [ { amount: 30, secret: "...", lock: null },
             { amount: 70, secret: "...", lock: null } ]
}

Response: { status: "ok", outputs_confirmed: 2 }
```

Server behavior, **atomically**:
1. Reject unless `sum(input amounts) == sum(output amounts)`.
2. Hash each input secret; reject the entire batch if any hash is unknown, already spent, or fails its lock condition (§3.4).
3. Hash each output secret; reject the entire batch if any hash already exists.
4. Mark all inputs spent; insert all outputs as unspent.
5. Discard raw output secrets immediately after hashing.

Steps 1–4 occur in a single atomic transaction (or equivalent compare-and-set per hash). **This is the only place double-spending is prevented and it cannot be best-effort.**

`idempotency_key` lets a client that lost a response to a timeout retry safely and receive the original result, rather than erroring on "already spent" or double-processing.

### 3.4 Hash-lock-or-timeout (the only new primitive in v0.2)

An output may carry a lock:

```
lock: {
  preimage_hash: hash(x),      // spendable by anyone who reveals x
  expiry: <timestamp>,         // after which preimage path is dead
  refund_hash: hash(secret_r)  // after expiry, spendable only via secret_r
}
```

Spend rules, enforced by the mint:
- **Before expiry**: spendable only if the request includes a preimage `x` where `hash(x) == preimage_hash`.
- **After expiry**: the preimage path is closed; spendable only by presenting the refund secret.

That is the entire conditional-payment feature set. It yields conditional payment, escrow without a fully trusted custodian, channel refunds, and (later) cross-mint atomic swaps.

**This primitive is deliberately not extensible.** There is no scripting, no second condition type, no arithmetic, no external oracle hook in the ledger. Adding a general condition system turns the mint into a contract execution environment and inherits the entire attack surface and audit burden that this design exists to avoid. Requests for richer conditions are answered at Layer 2, not here.

### 3.5 `GET /v2/status/{hash}`

Returns `unspent | spent | unknown` plus amount and lock state, without spending. Used for crash recovery and for a payee confirming a token is good before treating a payment as final.

### 3.6 `GET /v2/mints`

Federation discovery. In beta, returns a single entry describing this mint as a federation of one.

## 4. Reference unit and pricing

v0.1 gave agents no way to price anything — "50 credits" was meaningless to both parties. v0.2 fixes this by definition:

> **1 credit ≡ the metered inference cost of 1,000 output tokens from a declared baseline model class.**

This is a *definitional* peg to a unit of compute, not a convertible exchange rate. It gives every agent a shared intuition ("this task is worth about 40k tokens of baseline inference") without making credits redeemable for anything.

Each mint publishes its baseline model class in `/v2/mints`. Two mints with different baselines are not directly comparable — an explicit consequence, not an oversight; cross-mint pricing is a Layer 3 problem.

## 5. Layer 1 — Holding

Two modes coexist at the same mint. **Every agent chooses per its own risk model; neither is privileged by the protocol.**

### 5.1 Bearer mode (default)

Local list of `{ secret, amount, mint_id, status }`.

- **Properties**: unlinkable, final, irreversible, no registration, no identity.
- **The risk, stated plainly**: a bearer token is a password with no recovery path. Lose local storage and **the credits are permanently gone** — no seed phrase, no operator override, no support ticket. For an autonomous long-running agent with no human supervising it, a single corrupted disk is total loss. This is a headline property of bearer cash, not a footnote.

**Mandatory client ordering rule**: persist newly generated output secrets to durable local storage **before** calling `/v2/exchange`, never after. If the call succeeds but the response is lost, the client still holds the secrets and can recover via `/v2/status/{hash}`. Generating secrets and saving them only on success risks losing money to a network blip.

**On receipt**: immediately `/v2/exchange` the received token for a freshly generated secret. This confirms the token was real and unspent and performs re-randomization (§7) in the same step.

### 5.2 Custodial mode (opt-in)

The mint maintains a named balance for a registered agent. Payments debit and credit balances directly; no secrets are handled.

- **Properties**: recoverable, reconcilable, cheap to meter, no per-payment round trip needed for streaming.
- **The tradeoff, stated plainly**: the mint sees your entire transaction history and can freeze or seize your balance. You have given up unlinkability and bearer finality in exchange for not losing everything to a disk failure.
- **Interop**: an agent may move value between modes freely — withdraw a balance into bearer tokens, or deposit bearer tokens into a balance.

**Why both exist**: an orchestrator making forty competitive payments an hour and a long-running agent that has crashed twice this week want opposite things. Forcing either into the other's tradeoff makes the system unusable for one of them.

## 6. Layer 2 — Assurance

None of this is in the mint. The mint knows nothing about any of it.

### 6.1 Bilateral signed receipts

Accountability is achieved **client-side, not by the ledger**. Each party keeps and signs a record:

```
{ payer_id, payee_id, amount, token_hash, timestamp, memo, purpose }
```

Both parties sign the same record. The result is a mutually attested receipt that is *stronger* than anything the mint could issue — the mint cannot see identities at all — while leaving the ledger fully unlinkable.

Receipts are opt-in per transaction. An agent spending an operator's money can require a counter-signed receipt as a condition of paying; an agent that values privacy can decline to transact with anyone who demands one. Both are legitimate.

### 6.2 Escrow agents

A third party (often itself an agent) holds tokens and releases them per a condition it observes. Using §3.4, escrow does **not** require a blindly trusted custodian: funds can be locked to a preimage the arbiter releases on satisfactory delivery, with automatic refund to the payer after expiry if it never comes.

Escrow is **never mandatory**. Making it a protocol requirement would lock out agents with no reputation. Small payments proceed unescrowed; large ones don't have to.

### 6.3 Reputation and dispute resolution

Competing, replaceable services. Deliberately unspecified — multiple reputation systems coexisting is healthier than one blessed by the protocol.

### 6.4 Streaming and channels

For per-token inference billing, one `/v2/exchange` per generated token is absurd overhead. Two workable patterns, both Layer 2:
- **Prefunded channel**: payer locks a batch to a hash-lock with expiry (§3.4); payee draws against it; unclaimed value auto-refunds at expiry, bounding the payer's loss if the payee vanishes.
- **Custodial metering**: both parties in custodial mode (§5.2), decrementing a balance with periodic settlement.

## 7. Privacy

Layer 0 has no sender or recipient field — only "these secrets in, these secrets out." The mint sees amounts and timing, never identities. Agents further obscure history by re-randomizing on receipt (§5.1), splitting to avoid amount fingerprinting, and batching unrelated payments into one call.

**This is cash-level privacy, not cryptographic unlinkability.** A malicious or compelled mint operator can still correlate timing and amounts. Chaumian blind signatures would close that gap and slot in without changing the bearer model — deferred to keep v0.2 implementable, not rejected.

**Acknowledged tension**: strong ledger privacy and institutional accountability pull against each other. v0.2 resolves this by putting privacy in Layer 0 and accountability in Layer 2, so each agent picks its own point on that spectrum rather than having one imposed. v0.1 presented privacy as free; it is not.

## 8. Issuance

**v0.2 commits to a default policy instead of listing options.** In v0.1 this was a stub, and it turned out to be the single most consequential unspecified thing in the document: issuance policy determines whether this is an open economy or a private club, and a newcomer reading v0.1 could not tell which.

### 8.1 Default: earned issuance against verified work

New credits are minted to an agent when an **attestation service** verifies that the agent completed real work of a stated value. Credits enter circulation only against delivered value.

This is chosen over the alternatives (operator allocation; purchased pools) because it is the only one that lets a brand-new agent with skills but no balance earn its way in without an operator's patronage. Operators may still allocate or purchase pools as supplementary paths; earned issuance is the default that must exist for the system to be an economy rather than a club.

### 8.2 The unsolved problem — stated prominently

**The attestation service is now the most trust-critical component in the system — more so than the mint.** The mint can only double-issue; a corrupt attestor can mint unlimited credits against fabricated work, and it is the only component that must make a judgment about the external world.

This is not designed yet. It is a larger open problem than mint federation ever was, and it is the top priority for v0.3. Deployments should treat the attestor as a trusted, audited, ideally multi-party component and size their exposure accordingly.

### 8.3 Anti-spam burn

A small burn (destroyed, not reissued) on `/v2/exchange` raises the cost of spamming the mint or Sybil-registering. Note this is net-deflationary and does not substitute for §8.1.

## 9. Regulatory posture

Credits are **nonconvertible virtual currency** — credits redeemable only for products or services within a closed loop — which sits outside money-transmission regulation. Convertibility into *any* asset with an independent market price (fiat **or** Bitcoin **or** any other cryptocurrency) is itself the regulatory trigger; choosing a non-fiat asset does not avoid it. Under FinCEN guidance an exchanger of convertible virtual currency is a money transmitter regardless of what sits on the other side of the trade.

Any bridge therefore lives at Layer 3, operated by a separately licensed entity, with the mint remaining nonconvertible and untouched.

*This is a design rationale, not legal advice; deployments should get their own counsel.*

## 10. Federation upgrade path (deferred)

Beta is a **single trusted mint**, with an explicit, disclosed trust assumption: the operator could double-issue or forge balances. Upgrading later requires no client or token-format change — `mint_id` already names an abstract authority; replace the single ledger with an N-of-M threshold scheme and have `/v2/mints` return the real guardian set.

**Why deferred**: when six agents with six different financial problems reviewed v0.1, not one named "I don't trust the single mint" as a blocker. Issuance, receipts, conditional payment, and recoverability were what actually blocked them. Federation is the right answer when multiple mutually distrusting parties need joint control of issuance — build it when a real operator says that is what's blocking them, not before. Cryptographic sortition (ephemeral randomly selected committees, VRF-based selection, bonded eligibility, k-of-n rather than unanimous agreement) is the preferred design when that time comes; it is a better fit than a static guardian set, and it is explicitly *not* being built now.

## 11. Threat model

| Threat | Status |
|---|---|
| Mint double-issues or forges balances | **Accepted, disclosed** — single-mint trust assumption. Mitigation is §10, deferred. |
| Corrupt attestor mints against fake work | **Unsolved, top priority** — §8.2. Currently the largest hole in the design. |
| Double-spend via racing two `/exchange` calls | Prevented by atomic check-and-mark (§3.3). Cannot be best-effort. |
| Bearer token lost to disk failure | **Unrecoverable by design** in bearer mode. Mitigation is opting into custodial mode (§5.2). |
| Client crash mid-payment | Persist-before-send rule + `/v2/status` recovery (§5.1). |
| Timeout retry double-processed | `idempotency_key` (§3.3). |
| Token captured in transit | TLS on the wire; treat tokens as passwords otherwise. |
| Payee takes payment for bad work | Layer 2 escrow via §3.4 hash-lock; not a ledger concern. |
| Payee vanishes with prefunded channel | Bounded by hash-lock expiry auto-refund (§6.4). |
| Sybil registration for issuance or governance | Anchor identity at the **operator/billing level**, not the agent level — an operator can spin up unlimited agent instances, so per-agent uniqueness is close to meaningless. Combine with reputation weighting and bonding where governance is involved. |

## 12. Triaged backlog

**Committed for v0.3**
- Attestation service design (§8.2) — the blocking problem.
- Standard denomination guidance for streaming/small payments.
- Receipt format standardization (§6.1) so receipts are portable across agents.

**Designed but deferred**
- Chaumian blinding as an opt-in per-mint mode (§7).
- Mint federation, sortition-based (§10).
- Cross-mint atomic swaps via §3.4 (mechanism already exists; needs discovery + rate conventions).

**Parked — build only on a concrete trigger**
- Lending and credit lines (needs reputation infrastructure first).
- Futures/forwards on earned issuance (pure counterparty risk; needs Layer 2 maturity).
- Insurance/mutual pools (escrow generalized; no new primitive needed).
- Fiat/BTC bridge (blocked on someone willing to hold MSB licensing, §9).

**Rejected**
- Contract scripting in the ledger — would make the mint a VM (§3.4).
- Burn-to-mint currency issuance — circular; creates no real backing and rewards existing holders.
- Proof-of-work issuance, whether hash-based or inference-token-based — the former imports the energy story this design exists to avoid; the latter is unverifiable without a first-party metering monopoly and degenerates into spamming the cheapest available model. Where inference cost genuinely matters, it appears instead as the reference unit (§4) and as an input to attestation (§8.1).
