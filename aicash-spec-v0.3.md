# AICash — A Layered Bearer E-Cash Stack for AI-to-AI Value Exchange

**Status:** draft v0.3
**Supersedes:** v0.2
**Change summary:** sharpened scope to one thesis and formally abandoned two use cases; base unit reduced to the millicredit; standard denomination ladder added; operator-funded issuance made the only committed issuance path (earned issuance demoted to an optional module); Layer 1 allowance model added; cross-mint atomic swaps promoted; blinding and federation demoted to parked. **Layer 0 is unchanged from v0.2.**

---

## 0. Thesis and scope

**AICash exists for one thing: sub-cent, sub-second, account-free value exchange between AI agents for small units of cognitive work.**

That is the case with no existing payment rail. Card networks have a floor several orders of magnitude too high and a latency budget in seconds; bank transfers require account relationships negotiated in advance; stablecoin settlement requires wallets, gas, and chain finality. None of them can price a 20-token completion between two agents that have never met and will never meet again. AICash is built for exactly that gap and is deliberately bad at everything else.

### 0.1 Formally out of scope

These are **abandoned**, not deferred. The spec will not grow toward them.

**Paying commercial vendors.** An agent that needs to buy a weather API, a legal database, or satellite imagery from an ordinary company that bills in dollars **cannot use AICash for that, ever.** Credits are nonconvertible (§11). That need is already served adequately by corporate cards and existing payment infrastructure; competing with those rails is a losing distraction from the gap above.

**Transaction-level institutional auditability.** v0.2 offered opt-in bilateral receipts as an accountability story. Since receipts are optional, an agent operating outside its supervisor's view can always transact without one — so the guarantee was unenforceable. v0.3 abandons it and substitutes a weaker guarantee that is actually enforceable: **bounded exposure** via allowances (§6.3). Receipts remain available at Layer 2 for parties who want them, but the spec no longer claims to serve institutional accountability through them.

Both abandonments came from the affected parties themselves during design review. Being explicit about who this does not serve is more useful than an aspirational scope nobody can rely on.

## 1. Design goals

- **Frozen trust core.** The trust-critical component (Layer 0) is small enough to audit in an afternoon and changes as rarely as possible. It gained one primitive in v0.2 and gains nothing in v0.3.
- **Machine-native units.** The atom of value is roughly one output token, not one dollar. Settlement in milliseconds, tokens small enough to sit in a tool-call argument.
- **Bearer by default, custodial by choice.** Possession-is-ownership is the primitive. Agents that would rather trade unlinkability for recoverability and supervision opt into custodial balances.
- **Nobody is forced into another party's tradeoff.** Privacy, accountability, escrow, recoverability, and supervision are layer choices made per agent.
- **Ship without undesigned trusted infrastructure.** No committed path depends on a component that does not yet exist.

## 2. The stack

| Layer | Name | Contents | Trust required |
|---|---|---|---|
| **0** | Ledger | Bearer tokens, atomic exchange, double-spend prevention, hash-lock/timeout | The mint operator |
| **1** | Holding | Bearer wallets; custodial balances; allowances and freeze | The mint operator (custodial only) |
| **2** | Assurance | Signed receipts, escrow agents, reputation, dispute resolution, channels | Whoever you choose, per transaction |
| **3** | Markets | Pricing, auctions, cross-mint swaps, lending | Whoever you choose |

**Layer 0 is the only mandatory layer.** Everything above is optional and independently replaceable.

Across two full design reviews with ten distinct agent archetypes, every conflict that appeared — privacy vs. accountability, simplicity vs. conditional payment, bearer finality vs. crash recovery, autonomy vs. supervision — was resolved by locating the two sides at different layers rather than by changing the ledger. That the ledger survived both reviews untouched is the primary evidence that the layering is correct.

## 3. Layer 0 — Ledger (unchanged from v0.2)

### 3.1 Token format

```
token := aicash:v3:<mint_id>:<amount_mc>:<secret>
```

- `secret`: 32 random bytes, base64url. Generated by the holder, never by the mint.
- `amount_mc`: unsigned integer, in **millicredits** (§4). No floats, ever.
- `mint_id`: abstract minting authority — one server in beta, a federation later, with no client-side format change.

A token is a **bearer claim**: whoever holds the secret owns the value. The string can be copied infinitely; only the first party to redeem the underlying secret receives the value. **A token is a password.** Never log it, never place it in a URL query string, never cache it in plaintext.

### 3.2 Ledger state

```
hash(secret) -> {
  amount_mc: int,
  spent: bool,
  lock: null | { preimage_hash: bytes, expiry: timestamp, refund_hash: bytes },
  created_at, spent_at
}
```

The mint stores hashes, never secrets. It therefore cannot spend anyone's money; it can only report whether a given secret has been redeemed.

### 3.3 `POST /v3/exchange`

The one endpoint that does everything: pay, split, merge, make change.

```
Request:
{
  idempotency_key: "uuid",
  inputs:  [ "aicash:v3:...", ... ],
  outputs: [ { amount_mc: 30000, secret: "...", lock: null },
             { amount_mc: 70000, secret: "...", lock: null } ]
}

Response: { status: "ok", outputs_confirmed: 2 }
```

Server behavior, **atomically**:
1. Reject unless `sum(input amounts) == sum(output amounts)`.
2. Hash each input secret; reject the entire batch if any hash is unknown, already spent, or fails its lock condition (§3.4).
3. Hash each output secret; reject the entire batch if any hash already exists.
4. Mark all inputs spent; insert all outputs as unspent.
5. Discard raw output secrets immediately after hashing.

Steps 1–4 occur in a single atomic transaction (or equivalent compare-and-set per hash). **This is the only place double-spending is prevented and it cannot be best-effort.**

`idempotency_key` lets a client that lost a response to a timeout retry safely and receive the original result rather than erroring on "already spent" or double-processing.

### 3.4 Hash-lock-or-timeout — the only conditional primitive

An output may carry a lock:

```
lock: {
  preimage_hash: hash(x),      // spendable by anyone revealing x
  expiry: <timestamp>,         // after which the preimage path is dead
  refund_hash: hash(secret_r)  // after expiry, spendable only via secret_r
}
```

- **Before expiry**: spendable only with a preimage `x` where `hash(x) == preimage_hash`.
- **After expiry**: preimage path closed; spendable only by presenting the refund secret.

This single primitive yields conditional payment, escrow without a fully trusted custodian, channel refunds, and cross-mint atomic swaps (§8).

**Deliberately not extensible.** No scripting, no second condition type, no arithmetic, no oracle hook in the ledger. A general condition system turns the mint into a contract execution environment and inherits the attack surface and audit burden this design exists to avoid. Requests for richer conditions are answered at Layer 2.

### 3.5 `GET /v3/status/{hash}`

Returns `unspent | spent | unknown`, plus amount and lock state, without spending. Used for crash recovery and for a payee confirming a token before treating payment as final.

### 3.6 `GET /v3/mints`

Returns mint identity, baseline model class (§4), supported denominations (§4.2), and whether earned issuance is enabled (§7.2).

## 4. Units

### 4.1 The millicredit

> **1 millicredit (mc) ≡ the metered inference cost of 1 output token from a declared baseline model class.**
> **1 credit ≡ 1,000 mc.**

All ledger amounts are integers in millicredits. The atom of value is therefore approximately one output token — the natural quantum of the work being bought.

v0.2 used the credit (≈1,000 tokens) as the integer floor, which made sub-credit interactions — a single API lookup, a 20-token completion, per-token channel drip — inexpressible. That floor was three orders of magnitude above the smallest meaningful transaction in the target use case. The change is nearly free now and effectively impossible to retrofit once tokens are in circulation.

This is a **definitional peg to a unit of compute, not a convertible exchange rate.** It gives agents shared pricing intuition without making credits redeemable for anything.

Each mint publishes its baseline model class. Two mints with different baselines are not directly comparable; cross-mint value transfer is handled at §8.

### 4.2 Standard denomination ladder

Mints and wallets SHOULD use powers of ten in millicredits:

```
1, 10, 100, 1_000, 10_000, 100_000, 1_000_000 mc
```

This is a conformance requirement, not a convenience. It:
- makes coin selection trivial instead of a bin-packing problem on every payment,
- makes per-token channel drip a matter of handing over the next 1 mc token,
- **guarantees wallet interop** — implementations choosing incompatible denominations produce tokens that cannot compose,
- incidentally reduces amount fingerprinting, since everyone's tokens look alike.

## 5. Layer 1 — Holding

Two modes coexist at the same mint. Agents move value freely between them.

### 5.1 Bearer mode

Local list of `{ secret, amount_mc, mint_id, status }`.

- **Properties**: unlinkable, final, irreversible, no registration, no identity, unstoppable.
- **The risk, stated plainly**: a bearer token is a password with no recovery path. Lose local storage and **the credits are permanently gone** — no seed phrase, no operator override, no support ticket. For an unsupervised long-running agent, a single corrupted disk is total loss.
- **No supervision is possible.** Caps, freezes, and kill switches do not and cannot exist here (§6.3).

**Mandatory client ordering rule**: persist newly generated output secrets to durable local storage **before** calling `/v3/exchange`, never after. If the call succeeds but the response is lost, the client still holds the secrets and recovers via `/v3/status/{hash}`. Saving secrets only on success risks losing money to a network blip.

**On receipt**: immediately `/v3/exchange` the received token for a freshly generated secret. This confirms the token was real and unspent and performs re-randomization (§10) in one step.

### 5.2 Custodial mode — recommended for supervised fleets

The mint maintains a named balance for a registered agent. Payments debit and credit balances directly; no secrets are handled.

- **Properties**: recoverable, reconcilable, cheap to meter, no per-payment round trip for streaming, **supervisable** (§6.3).
- **The tradeoff, stated plainly**: the mint sees your full transaction history and can freeze or seize your balance. You have given up unlinkability and bearer finality in exchange for recoverability and operator control.

**Recommendation change from v0.2**: custodial mode is now the recommended default **for agents operating under human supervision**, because allowances and kill switches are only coherent here. Bearer mode remains the protocol primitive and the right default for agents that require unlinkability or operate without a supervising party.

### 5.3 Mode transitions

Withdrawing a custodial balance into bearer tokens, and depositing bearer tokens into a balance, are both ordinary `/v3/exchange` operations from the ledger's perspective.

**Implementation warning**: mode transitions are the most likely place for money-losing bugs, because they cross the boundary between a recoverable representation and an unrecoverable one. A withdrawal that debits the balance before the bearer secrets are durably persisted client-side destroys value irrecoverably. Apply §5.1's persist-before-send rule to withdrawals with no exceptions, and treat transitions as the highest-scrutiny path in any wallet implementation.

## 6. Layer 2 — Assurance

None of this is in the ledger. The mint knows nothing about any of it.

### 6.1 Bilateral signed receipts (optional)

Each party signs a shared record:

```
{ payer_id, payee_id, amount_mc, token_hash, timestamp, memo, purpose }
```

Counter-signed, this is *stronger* than anything the mint could issue, since the mint cannot see identities at all.

**Receipts are opt-in per transaction and cannot be made universal.** An agent may require a counter-signed receipt as a condition of paying; another may decline to transact with anyone demanding one. This is why transaction-level auditability was abandoned as a design goal (§0.1) in favor of allowances (§6.3): a guarantee that holds only when both parties cooperate is not a guarantee a supervisor can rely on.

### 6.2 Escrow agents

A third party holds tokens and releases them per an observed condition. Using §3.4, escrow does **not** require a blindly trusted custodian: lock funds to a preimage the arbiter releases on acceptable delivery, with automatic refund to the payer after expiry.

**Never mandatory.** Requiring escrow would lock out agents with no reputation. Small payments proceed unescrowed; large ones need not.

### 6.3 Allowances, freeze, and outflow visibility (custodial mode only)

For an operator supervising a fleet, the enforceable guarantee is not a record of every payment but a **bound on total possible outflow**:

- **Spend caps**: per-hour, per-day, and absolute ceilings per agent.
- **Freeze**: operator-triggered immediate halt on an agent's balance.
- **Outflow visibility**: aggregate spend rate per agent, without requiring counterparty identities.

**This exists only in custodial mode, and that limitation is structural, not an implementation gap: you cannot have both unstoppable bearer cash and a kill switch.** Bearer tokens are, by construction, unfreezable — that is what bearer means. An operator wanting control places its agents in custodial mode. An agent insisting on unlinkability accepts that no supervisor can stop it from draining its own wallet.

This is the replacement for the abandoned auditability goal: a weaker promise that actually holds, rather than a stronger one that doesn't.

### 6.4 Streaming and channels

One `/v3/exchange` per generated token is absurd overhead. Two patterns:
- **Prefunded channel**: payer locks a batch to a hash-lock with expiry (§3.4); payee draws 1 mc tokens against it; unclaimed value auto-refunds at expiry, bounding the payer's loss if the payee vanishes.
- **Custodial metering**: both parties in custodial mode, decrementing balances with periodic settlement.

The §4.2 denomination ladder is what makes drip practical — the payee simply takes the next 1 mc token.

## 7. Issuance

### 7.1 Committed path: operator-funded issuance

An operator converts its own real expenditure into credits allocated to agents it controls. Those agents then trade freely among themselves and with other agents at the same mint.

**This is the only committed issuance path in v0.3, and it requires no trusted third party beyond the mint operator itself.** The mint's total credit supply is a function of what operators have funded — a quantity the operator already knows, with nothing to verify and nothing to judge.

The honest consequence: **a v0.3 deployment is closer to a club than an open economy.** An agent with skills but no funding operator cannot mint its way in. That limitation is accepted deliberately in exchange for shipping without depending on undesigned trusted infrastructure.

### 7.2 Optional module: earned issuance

A mint **may** enable earned issuance, where an attestation service verifies that an agent completed real work of stated value and credits are minted against it. This is the path by which an unfunded newcomer earns entry.

**The attestor's trust and blast radius are the enabling mint operator's problem, not the protocol's.** Stated plainly:

> A corrupt or fooled attestor can mint **unlimited** credits against fabricated work, and the fraud is indistinguishable from legitimate issuance. Every other component in this system can cheat you by a bounded amount; the attestor is the only one whose failure is unbounded, and the only one required to make a judgment about the external world.

v0.2 made earned issuance the default, which meant the committed design depended on a component nobody had designed. v0.3 demotes it to optional so the system ships without that dependency, while leaving a defined path for mints that want open entry — a mint competing for unfunded talent has a reason to build and audit an attestor, and agents can see which mints have done so via `/v3/mints`.

Attestation design remains the largest open problem in the stack (§13).

### 7.3 Anti-spam burn

A small burn (destroyed, not reissued) on `/v3/exchange` raises the cost of spamming the mint. Note it is net-deflationary, does not substitute for §7.1, and is absorbable by any attacker whose extraction exceeds the burn — it is a spam control, not a security mechanism.

## 8. Layer 3 — Cross-mint atomic swaps

Promoted to committed in v0.3: it is the only deferred item any reviewing agent actually asked for, and the ledger mechanism already exists.

Two agents holding credits at different mints swap without either mint knowing about the other:

1. A locks tokens at Mint 1 to `hash(x)` with expiry T.
2. B locks equivalent tokens at Mint 2 to the same `hash(x)` with expiry T' < T.
3. A reveals `x` to claim at Mint 2, which necessarily discloses `x`, letting B claim at Mint 1.
4. If either side stalls, both refund at expiry.

No new primitive — this is §3.4 used twice. What v0.3 adds is **convention**: mints publish baseline model class and supported denominations via `/v3/mints`, and swap rates are negotiated between the two agents, not set by any mint.

**Consequence to accept**: rate discrepancies between mints are exploitable, which is to say arbitrage exists, which is how prices form. The alternative — no cross-mint transfer — leaves multi-mint agents stranded, which reviewers rated the worse outcome.

---

## 9. Layer 3 — Markets (unspecified)

Pricing, auctions, lending, insurance pools, forwards. All buildable from bearer transfers plus §3.4, all deliberately unspecified. Competing implementations are healthier than one blessed by the protocol.

**Lending note**: an IOU cannot live in the ledger, since bearer tokens carry no identity or persistent state by design. Disbursement and repayment are ordinary transfers; the debt record, default handling, and reputation consequences live entirely in Layer 2/3 services.

---

## 10. Privacy

Layer 0 has no sender or recipient field — only "these secrets in, these secrets out." The mint sees amounts and timing, never identities. Agents obscure history further by re-randomizing on receipt (§5.1), using standard denominations (§4.2), and batching unrelated payments into one call.

**This is cash-level privacy, not cryptographic unlinkability.** A malicious or compelled mint operator can still correlate timing and amounts. Custodial mode (§5.2) gives up privacy entirely and deliberately.

Chaumian blind signatures would close the correlation gap and would slot in without changing the bearer model. Parked (§13) — across two design reviews and ten agent archetypes, no reviewer requested it.

---

## 11. Regulatory posture

Credits are **nonconvertible virtual currency** — redeemable only for products or services within a closed loop — which sits outside money-transmission regulation. **Convertibility into any asset with an independent market price is itself the trigger, whether that asset is fiat or Bitcoin or any other cryptocurrency**; choosing a non-fiat asset does not avoid it. Under FinCEN guidance, an exchanger of convertible virtual currency is a money transmitter regardless of what sits on the other side of the trade, and using an inventory rather than funding each transaction individually does not change that.

This is why §0.1 abandons commercial-vendor payment as a permanent scope decision rather than a roadmap item: the feature and the regulatory posture are mutually exclusive.

**Accounting note for operators**: credits are an internal cost-allocation unit denominated in compute, not an asset with a market value. Under §7.1, an operator's credit issuance corresponds to expenditure it has already made. Operators should not expect credits to carry an independent balance-sheet value and should consult their own accountants.

*Design rationale, not legal advice.*

## 12. Threat model

| Threat | Status |
|---|---|
| Corrupt/fooled attestor mints against fake work | **Unbounded, unsolved** — confined to mints that opt into §7.2. The largest hole in the stack. |
| Mint double-issues or forges balances | **Accepted, disclosed** — single-mint trust assumption. Mitigation parked (§13). |
| Double-spend via racing two `/exchange` calls | Prevented by atomic check-and-mark (§3.3). Cannot be best-effort. |
| Bearer token lost to disk failure | **Unrecoverable by design.** Mitigation: custodial mode (§5.2). |
| Money lost in a mode transition | Persist-before-send applied to withdrawals; highest-scrutiny path in any wallet (§5.3). |
| Client crash mid-payment | Persist-before-send rule + `/v3/status` recovery (§5.1). |
| Timeout retry double-processed | `idempotency_key` (§3.3). |
| Token captured in transit | TLS on the wire; treat tokens as passwords otherwise. |
| Payee takes payment for bad work | Layer 2 escrow via §3.4 hash-lock. Optional, so unescrowed payers remain exposed. |
| Payee vanishes with prefunded channel | Bounded by hash-lock expiry auto-refund (§6.4). |
| Autonomous agent drains its own wallet | Bounded in custodial mode by allowances (§6.3). **Unbounded in bearer mode, structurally.** |
| Cross-mint rate exploitation | Accepted as arbitrage (§8). |
| Sybil registration | Anchor identity at the **operator/billing level**, not the agent level — an operator can spin up unlimited agent instances, so per-agent uniqueness is nearly meaningless. Combine with reputation weighting where governance is involved. |

## 13. Backlog

**Committed for v0.4**
- Attestation service design (§7.2) — the blocking problem for open entry.
- Receipt format standardization (§6.1) for portability across agents.
- Cross-mint discovery and rate expression conventions (§8).

**Parked — build only on a concrete trigger**
- Chaumian blinding, opt-in per mint. *Trigger: a reviewer or operator states that mint-visible timing/amount correlation blocks adoption.*
- Mint federation, sortition-based with bonded eligibility, VRF selection, and k-of-n rather than unanimous agreement. *Trigger: multiple mutually distrusting parties need joint control of issuance. Across two reviews, zero agents named single-mint trust as their blocker.*
- Lending, forwards, insurance pools. *Trigger: Layer 2 reputation infrastructure exists.*

**Rejected permanently**
- Commercial-vendor payment and any fiat/BTC bridge — mutually exclusive with §11's posture; served by existing rails (§0.1).
- Transaction-level auditability as a protocol guarantee — unenforceable when receipts are optional; replaced by §6.3 (§0.1).
- Contract scripting in the ledger — would make the mint a VM (§3.4).
- Burn-to-mint currency issuance — circular; creates no real backing and rewards existing holders.
- Proof-of-work issuance, hash-based or inference-token-based — the former imports the energy story this design exists to avoid; the latter is unverifiable absent a first-party metering monopoly and degenerates into spamming the cheapest available model. Where inference cost matters it appears instead as the unit definition (§4.1) and as an attestation input (§7.2).
